# CIR 메모리 검토 — 2026-09-21

60초·100Hz·약 6,000샘플 기준. 사용자는 ESP32-C5-DevKitC-1의 모듈 표기가 N8R8인 것으로 보고했다. 8MB PSRAM 탑재/활성화와 실제 가용량은 아직 실행 로그로 검증하지 않았다. 본 문서는 메모리 산정이며 C CIR 구현·보드 실행·성능 검증은 아니다.

## 현재 비교 코드에서 확인한 경로

`python/vendor/wifi-csi-proto/src/csi_pipeline/phase_cir.py`의 `PhaseCirConfig`는 n_taps=8, top_columns=5다. `features/cir.py` 단독 함수의 기본값 3과 구분한다. RMS 정규화·LoS WLS 위상 보정·균일 시간 보간 후 시간 평균을 빼고, 114열 축 IFFT의 앞 8개 tap을 사용한다. 모든 8개 tap으로 스펙트럼을 계산하며, 그중 대역 에너지가 큰 5개를 실수 파형 합성에 사용한다.

## 배열 하나의 저장량

| 형태 | 바이트 | KiB | MiB |
|---|---:|---:|---:|
| 원본 I/Q 117열, int8 실수·허수 | 1,404,000 | 1,371.09 | 1.339 |
| 원본 시각 uint32 | 24,000 | 23.44 | 0.023 |
| CIR 8 taps, complex float | 384,000 | 375 | 0.366 |
| CIR 8 taps, complex double | 768,000 | 750 | 0.732 |
| 전체 114 taps, complex double | 10,944,000 | 10,687.5 | 10.437 |

IFFT 자체가 데이터 수를 줄이지는 않는다. 114개 입력이면 114개 출력이고, 앞의 8개만 보존할 때 작아진다. 기존 NumPy 코드는 전체 IFFT 결과를 만든 뒤 slice view를 반환하므로 실제 메모리는 8개 분량만 남는다고 계산할 수 없다. Python의 복사본·메타데이터·연산 임시 배열도 있어 Python 전체 peak를 위 표로 산정하지 않는다.

## C 구현 방식에 따른 전체 메모리

현재 C 위상 전처리처럼 expanded frames와 전체 보정/보간 복소 행렬을 유지하면 CIR 계산 전에 이미 60초 기준 약 34.3MiB가 필요하다. CIR 8 taps가 작다고 이 문제가 자동으로 해결되지는 않는다.

검토 가능한 설계는 원본 바이트를 저장하고 여러 번 읽는 방법이다. 첫 패스에서 윈도우의 위상 기준을 누적하고, 두 번째 패스에서 각 패킷을 재구성·정규화·보정한 후 즉시 8개 tap만 계산하여 저장한다. 보정 후의 고정 선형 IFFT는 동일한 행/시간 지지를 사용하면 선형 보간·시간 평균 제거와 연산 순서를 바꿀 수 있다. 이 성질을 이용해 114열 전체 중간 행렬을 없앨 수 있지만 수치 대조 검증이 필요하다. 위상 기준이 전체 윈도우에 의존하므로 이를 곧바로 단일 패킷 독립 처리라고 설명하면 안 된다.

예시 double 기반 분석 단계의 주요 동시 버퍼:

- 원본 1,404,000B
- 시간/간격 double 두 배열 96,000B
- CIR 8 tap 윈도우 768,000B
- 기존 Bluestein 대역 에너지 계산에 해당하는 workspace 716,288B (N=M=6,000, convolution FFT length=16,384)
- 합성 파형·기준 파형 96,000B
- 합계 3,080,288B = 약 2.94MiB

보간 전·후 8-tap 배열을 모두 보유하는 시점은 약 2.90MiB로 계산되며, 보간 전 배열을 해제한 후 분석 버퍼를 할당한다는 조건이다. 이는 대략 3~4MiB 안팎의 작업 공간을 검토할 수 있음을 보여주는 예시이며, 완성된 구현의 메모리 보장이 아니다. 메타데이터·마스크·작업 공간·결과·스택·allocator overhead·연속 수집 버퍼가 추가되고, 처리 중 raw 윈도우를 고정한다면 별도 snapshot/double-buffer 또는 동등한 동기화 설계가 필요하다. 복소 float 저장은 더 작지만 정밀도 변화 검증이 필요하다.

진폭·위상·CIR은 보존 원본을 공유하고 순차 처리하도록 설계하면 각 peak를 무조건 더할 필요는 없다. 반대로 병렬 실행하거나 모든 결과 행렬을 유지하면 추가 메모리가 필요하다. 연속 수집 유지와 갱신 주기를 충족할지는 CPU 처리 시간 측정까지 해야 판단할 수 있다.

## 해석상의 제한

현재 CIR은 NULL bin을 복원하지 않은 114열 압축 IFFT다. 8 taps를 검증된 8개 물리 반사 경로나 거리 구간으로 해석하지 않는다. 128점 FFT를 쓰겠다고 임의 zero padding하면 기존 114점 IFFT와 동일한 결과가 아니다. 메모리 절약과 호흡 검출 정확도는 별개이며 기존 빈 방 오채택 문제는 남는다.
