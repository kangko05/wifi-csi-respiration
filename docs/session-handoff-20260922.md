## 재개 시 먼저 확인할 내용

**현재 작업은 사용자가 방향을 고민하는 단계에서 멈췄다.** 고정소수점 FFT
검증(B0)은 제안·검토만 했고 아직 구현하지 않았다. 이번 요청은 진행 상황
저장이며, B0나 전체 실시간화 계획의 실행 승인이 아니다.

사용자가 마지막으로 구체화한 목표는 다음과 같다.

- 약 60초 윈도우를 유지하면서 **최신 윈도우 분석 + 외부 수신기로 결과 전달을
  최대 3초 안에 완료**, 다음 최신 윈도우로 같은 과정을 반복한다.
- 분석 중에도 수신·윈도우 갱신은 계속되어야 한다.
- 과거 문서의 1초 예산과 구분한다. 최근 대화의 목표는 3초 주기다.
- 현재 외부로 보내는 결과 전송은 미구현이다. 출력 경계는 나중에 교체할 수
  있도록 `csi_output.c/.h`에 분리했다.
- 온보드 연산이 반드시 필요한지, 외부 장치(라즈베리파이 등)에서 계산해도
  되는지는 프로젝트 리더에게 확인할 예정이며 아직 답을 받지 않았다.

## 현재 구현과 보드 상태

- RX: ESP32-C5, 240 MHz 단일 코어, 8 MiB PSRAM 활성화, Quad 40 MHz.
  ESP-IDF v6.0.3, 성능 최적화 `-O2` 빌드.
- 마지막 확인 RX 포트는 `/dev/ttyUSB0`. 9월 21일에는 TX/RX 연결 확인 후
  직접 플래시·측정했고 마지막 모니터는 종료했다. 다음 세션의 현재 연결
  상태는 미확인이므로 포트 작업 전에 현장 준비 상태를 확인한다.
- 수신 콜백 → 200개 큐 → 처리 태스크 → PSRAM 원시 윈도우 구조.
- 원시 윈도우: 6,600개 용량 × 레코드 540 bytes = **3,564,000 bytes**.
  약 100 Hz에서 60초가 차면 실제 저장 수는 약 6,000개로 유지된다.
- 진폭 raw 경로는 칸별 작업 버퍼를 재사용하고, FIR의 남길 출력만 계산한다.
  4,096점 double FFT 회전 계수 표 32,768 bytes를 부팅 시 만들어 재사용한다.
- 일반 모드는 **부팅당 진폭 분석 한 번**만 수행하는 시험 파이프라인이다.
  수집 큐 소비와 분석이 같은 태스크라 분석 중 큐가 포화한다.
- 처리 태스크 스택은 8,192 bytes. 위상·CIR의 보드 실시간 연결은 하지 않았다.

마지막 플래시 및 현재 `csi-rx/sdkconfig` 설정:

```text
# CONFIG_CSI_RX_AMP_BENCHMARK is not set
CONFIG_CSI_RX_AMP_FLOAT_MATH=y
CONFIG_CSI_RX_AMP_FFT_OVERSAMPLING=4
```

즉 **FFT/FIR 단정밀도만 기본 적용**, 출력률 10 Hz와 전체 유효 칸 분석은
유지한다. FFT 길이 축소·5 Hz·top16·스트리밍은 실험으로 남겼다.
호스트 기준 경로와 옵션을 주지 않은 raw API는 기존 수치 경로를 유지한다.

## 완료한 실험과 결과

RX에서 약 60초 입력을 한 번 수집한 뒤 CSI 수신을 끄고 같은 입력으로
11개 변형을 순서대로 측정했다. 5,991개 레코드 × 117칸,
입력 fingerprint `496265c1`. 끝에서 baseline을 반복해 전체 결과의
byte 일치와 시간 차이 약 0.073%를 확인했다.

아래는 설정·선행 전처리·분석·해제·결과 로그를 포함한 **총시간**이다.

| 변형 | 총시간 | 판정 |
| --- | ---: | --- |
| 기준 double 경로 | 56.011초 | 비교 기준 |
| FFT/FIR float만 | 37.395초 | 일반 RX에 적용 |
| PSD FFT oversampling 4 → 1만 | 45.149초 | 실험 옵션 |
| 출력률 10 → 5 Hz만 | 33.808초 | 실험 옵션 |
| 분산 기반 top16만 | 10.785초 | 후보 손실로 기본 적용 제외 |
| 스트리밍 전처리만 | 68.026초 | 총시간 증가 |
| float + FFT 축소 | 31.569초 | 실험 옵션 |
| float + FFT 축소 + 5 Hz | 22.378초 | 실험 옵션 |
| 위 조합 + top16 | 6.038초 | 후보 손실 포함, 3초도 미달 |
| 위 조합 + 스트리밍 | 20.044초 | 선행 전처리까지 포함 |

스트리밍 단독은 최종 분석 33.557초에 앞선 전처리 34.361초가 추가된다.
단일 push 최대 49.746 ms, 추가 상태 376,412 bytes였다. 이 구현은
한 윈도우의 패킷별 전처리이며 **이동 윈도우 재사용은 아직 지원하지 않는다.**
고정 길이, first_word_invalid=0, 최대 100 ms 간격 조건에서만 동작한다.

### 기존 결과 대조

- 루트 테스트 **25개 통과**. 기록은 9월 21일 실행 결과이며 문서 저장을 위해
  테스트를 다시 실행하지 않았다.
- 녹화 21개의 처음 60초를 변형별로 대조했다.
- float 단독: 최종 채택 여부·최고 점수 칸·개별 칸의 채택 여부가 모두 동일.
  최대 score 차이는 약 0.000001561. 일반적인 모든 입력에서 동일하다는 보장은 아니다.
- FFT 축소: 최종 채택 여부는 같지만 최고 점수 칸이 2개 녹화에서 바뀌고
  개별 칸의 채택 판정도 총 29건 바뀌었다.
- 5 Hz: 최종 채택 여부가 2개 녹화에서 바뀌었다.
- top16: 기준에서 채택된 녹화 5개 중 4개를 놓쳤다.
- 스트리밍 단독은 기준과 전체 결과가 byte 일치. combined_stream도
  combined와 전체 결과가 byte 일치했다.
- 이는 수치·회귀 검증이며 실제 호흡/무호흡 정확도 검증은 아니다.

### 일반 수신 모드 복귀 실측

벤치마크를 끄고 float만 켠 일반 RX를 다시 플래시했다. 정상 부팅,
윈도우 축적, 분석 완료까지 확인했다.

- 분석 **38.286초**, 종료 시 queued=200.
- withheld, bin=53, PSD 3.369 bpm, ACF 45.453 bpm, reasons=0xa0.
- 유효성 검사 2.541초, 보간 9.956초, FIR 6.774초,
  detrend 0.786초, PSD 8.847초, ACF 7.815초.
- FFT가 포함된 PSD+ACF 약 44%, 보간+FIR도 약 44%다.
  단계 시간 전부를 순수 FFT나 캐시 미스 비용으로 해석하면 안 된다.
- 분석 후 내부 힙 free=95,955 bytes, largest=43,008 bytes,
  누적 min_free=26,028 bytes. PSRAM free=4,762,632 bytes.
- 큐가 찬 직후 queue_drops=0은 드롭이 없다는 증거가 아니다.
  드롭 카운터는 이후 수신 레코드를 통해 전달된다.

## 고정소수점 계획 검토 — 미구현

사용자가 제시한 Claude 계획:
[rx-amplitude-realtime-plan-20260921.md](rx-amplitude-realtime-plan-20260921.md).
권장 순서는 B0(정수 FFT 검증) → A(증분 전처리) → B(정수 스펙트럼 처리)
→ C(주기 처리·태스크 분리)다. 문서의 구현 지시가 곧 이번 실행 승인은 아니다.

검토 결론: **3초 목표를 노려볼 가능성은 있으나 아직 입증되지 않았다.**
중복 제거만으로 13배 개선을 기대하는 것과, 소프트웨어 실수 연산을
고정소수점으로 바꾸고 겹치는 시간 구간을 재사용하는 것은 다른 변경이다.
앞선 대화에서 하드웨어만으로 어렵다고 단정하거나, 반대로 1초를 예상하는
주장을 확정 사실로 이어받지 않는다.

보완해야 할 구체적 사항:

1. 실제 빌드의 `csi-rx/build/toolchain/cflags`는
   `-march=rv32imac_zicsr_zifencei_zaamo_zalrsc`다. 실수 연산 비용을 줄일
   가능성은 있지만 Q15 25~40 cycle 등은 아직 보드 측정치가 아니다.
2. 현재 117칸의 radix-2 FFT butterfly 수는 약 **551만 개**다.
   문서의 430만 개 및 FFT 묶음 처리 후 예상 연산량은 별도로 재산정해야 한다.
3. 내부 RAM에 117칸 × 201탭 × int16 × 이중 기록 FIR 링을 두면
   **94,068 bytes**가 필요하다. 현재 약 96KB 여유와 43KB 최대 블록에서
   FFT 작업 버퍼까지 그대로 넣을 수 없다. 큐·버퍼 배치 예산부터 조정해야 한다.
4. PSRAM 캐시 미스가 큰 원인이라는 가설은 타당하지만, 미스 횟수/지연을
   직접 측정하지 않았다. 전처리 CPU 1%, 총 0.6~1.3초, 비관 2~3초는 추정이다.
5. Q15 스케일링·반올림·오버플로 때문에 약한 신호가 사라지지 않는지 확인한다.
   정수 진폭도 소수부 정밀도 보존이 필요하다. 부족하면 Q31을 검토한다.
6. 현재 `prepared`는 시간×칸 배치이며 raw 검증/eligibility를 다시 수행한다.
   계획의 칸×시간 축소 버퍼와 증분 통계를 쓰려면 API 변경이 필요하다.
7. 겹치는 57초의 원시 입력이 같아도 윈도우 기준 시각에 따른 보간 격자,
   필터 경계, 유효성 마스크가 달라질 수 있다. 재사용 계약과 비교 오차를 정의한다.
8. PSD FFT 4096점과 ACF FFT 2048점을 묶어 처리하려면 길이 정합과
   정규화 설계까지 검증한다. 태스크 분리만으로 총 CPU 연산량이 줄지는 않는다.

사용자가 온보드 실험을 계속하기로 결정하면 **B0만 먼저** 수행하는 것이
합리적이다. 정수 FFT/PSD/ACF의 보드 시간과 기존 녹화의 판정 변화를 보고
전체 구조 변경에 투자할지 판단한다. 다른 선택지는 같은 입력·알고리즘을
외부 장치에서 돌려 계산과 전송을 합쳐 3초 이내인지 측정하는 것이다.

## 요구사항상 아직 별도인 문제

현재 구현은 주기 후보/BPM 추정이다. 60초 윈도우에서 최근 10초의 활동 감소를
판정하는 로직이나 무호흡 경보는 구현하지 않았다. 무호흡에 관해 대화한
10초는 성인 수면검사의 사건 지속시간 기준이며, CSI 임계값이나 계산 예산을
자동으로 정해 주지 않는다. 프로젝트가 요구하는 대상과 경보 지연을 확인해야 한다.
